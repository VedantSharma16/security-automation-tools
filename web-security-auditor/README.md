# Web Security Auditor

A recon tool for web application security assessments: point it at a URL and
it checks security headers, cookie flags, CORS policy, TLS configuration, and
common sensitive-path exposure, then produces a scored, OWASP-Top-10-mapped
report — with an optional LLM-generated executive narrative.

Where the other tools in this repo triage host/log telemetry after an
incident (blue team), this one is recon/assessment tooling from the
red-team/pentest side of the same workflow: the kind of pass you'd run at the
start of an engagement or before a release ships.

> **Authorized use only.** This tool sends live HTTP(S) requests (including
> probes for exposed paths like `/.git/HEAD` and a cross-origin CORS test) to
> the target. Only run it against hosts you own or have explicit permission
> to test.

## What it checks

| Module | Checks | OWASP mapping |
|---|---|---|
| `headers.py` | HSTS, CSP (incl. `unsafe-inline`/`unsafe-eval`), `X-Content-Type-Options`, clickjacking protection, `Referrer-Policy`, `Permissions-Policy`, `Server`/`X-Powered-By` version disclosure, cookie `Secure`/`HttpOnly`/`SameSite` flags | A02, A05 |
| `cors.py` | Reflected/wildcard `Access-Control-Allow-Origin`, especially combined with `Access-Control-Allow-Credentials: true` | A01 |
| `tls.py` | Certificate expiry/expired, outdated protocol (< TLS 1.2), weak cipher suites | A02 |
| `disclosure.py` | Exposed sensitive paths (`.git/HEAD`, `.env`, backup files, etc. — see [`rules/sensitive_paths.yaml`](rules/sensitive_paths.yaml)), interesting `robots.txt` entries | A05 |

Every finding carries a severity (`info` → `critical`), an OWASP Top 10
(2021) category, evidence, and a remediation suggestion. Findings roll up
into a 0–100 risk score and an overall rating (`none`/`low`/`medium`/`high`/`critical`).

## Install

```bash
cd web-security-auditor
pip install -e ".[dev]"       # + "[llm]" for the optional Claude-generated narrative
```

Zero required third-party dependencies beyond `PyYAML` (for the sensitive-path
rule file) — no `requests`, everything runs over the standard library's
`urllib`/`ssl`/`socket`.

## Usage

```bash
web-security-audit https://example.com
web-security-audit https://example.com --min-severity medium --json-out report.json --markdown-out report.md
web-security-audit https://example.com --narrative        # add an analyst summary
web-security-audit https://example.com --skip-disclosure   # skip sensitive-path probing
```

Exit codes: `0` = clean, `1` = findings reported, `2` = usage/URL error — so it
slots into CI as a release gate (`web-security-audit $URL --min-severity high`).

Sample output (see [`examples/sample_report.md`](examples/sample_report.md) /
[`examples/sample_report.json`](examples/sample_report.json) for a full run
against a real target):

```
Web Security Auditor — https://pypi.org
Findings: 3  |  Risk score: 15/100  |  Rating: MEDIUM

[MEDIUM  ] TLS certificate expires in 26 day(s) (A02:2021 Cryptographic Failures)
           evidence: notAfter=Sep 19 23:34:02 2026 GMT
           fix: Renew the certificate before expiry; consider automated renewal (e.g. ACME/Let's Encrypt).
```

### Analyst narrative

`--narrative` produces an executive-summary paragraph. With `ANTHROPIC_API_KEY`
set (and `pip install -e ".[llm]"`), it's generated by Claude from the
structured findings; without a key, a deterministic offline summary is used
instead, so the tool — and its tests — never depend on network access or an
API key. Same pattern as [`ioc-triage-assistant`](../ioc-triage-assistant/)
and [`log-triage-assistant`](../log-triage-assistant/) in this repo.

## Design notes

- **One seam for network I/O.** `Fetcher.get()` and `get_tls_info()` are the
  only two functions that touch a socket. Every checker takes them (or a
  fake) as a parameter, so the entire test suite runs offline against
  hand-built `FetchResult`s and fake TLS info — no mocking framework, no
  real network calls, no flaky tests.
- **CORS probe, not header inspection.** Rather than just reading whatever
  CORS headers happen to be on the base response, `cors.py` sends a second
  request with a deliberately unrelated `Origin` header and checks whether
  the server reflects it — that's what actually distinguishes an allowlist
  from a rubber stamp.
- **Declarative sensitive-path rules.** `rules/sensitive_paths.yaml` follows
  the same rule-file convention as [`process_threat_hunter`](../process_threat_hunter/)'s
  `default_rules.yaml` — extend the list per engagement without touching code.

## Tests

```bash
pytest
```

62 tests, all offline (mocked `urlopen`/TLS info, no live requests), covering
every checker module, scoring, report rendering, the CLI, and the LLM
narrative's offline fallback path.

## Limitations

This is a recon/triage aid, not a substitute for a full penetration test:
- It does not do active exploitation, form/injection testing, or auth-aware
  crawling — headers, cookies, CORS, TLS, and a small fixed list of sensitive
  paths only.
- The CORS check runs a single unauthenticated GET probe, not a full
  preflight (`OPTIONS`) simulation.
- TLS analysis reads what Python's `ssl` module negotiates by default; it
  doesn't enumerate every cipher/protocol the server supports the way a
  dedicated scanner (e.g. `testssl.sh`) does.
