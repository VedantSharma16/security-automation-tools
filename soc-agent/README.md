# SOC Agent

An agentic SOC alert-triage playbook runner. Given a raw alert (host,
IPs, user, process), the agent autonomously decides which internal
systems to query — asset inventory, threat intel, identity risk, EDR
process baseline — investigates only what's relevant to the fields
actually present, and produces a scored verdict with concrete
containment actions and a full, auditable investigation trace.

Live mode drives this with Claude's tool-use API: the model itself
chooses which tools to call, in what order, and when it has enough
evidence to submit a verdict. Without an API key, a deterministic
offline planner runs the exact same tool functions and scoring logic,
so the whole pipeline is fully runnable and testable with zero network
access.

## Why this exists

The other tools in this repo (`ioc-triage-assistant`, `log-triage-assistant`)
are retrieval and rule-based pipelines: fixed steps, LLM used at the end for
narrative generation. This project demonstrates the other half of applied AI
engineering — an **agentic loop**, where the model itself performs
multi-step, data-dependent tool orchestration rather than following a
hardcoded sequence. An alert with no `username` field never triggers a
user-risk lookup; an alert with no `process_name` never triggers a baseline
check. That branching is real agent behavior, not a template.

Keeping an offline planner that calls the *same* tool implementations means
the two modes can't silently diverge, and the project stays honest about
what's real: the "systems" being queried (`data/*.json`) are small synthetic
datasets standing in for a CMDB, a threat-intel feed, an IdP risk API, and
an EDR baseline — the seam where a real integration would go.

## How the agent loop works

```
Alert (JSON)
      │
      ▼
 SecOpsAgent.investigate()
      │
      ├── live mode (ANTHROPIC_API_KEY set) ──────────────────────────┐
      │     Claude picks tools from soc_agent/tools.py based on which │
      │     alert fields are present, calls them in a loop, then      │
      │     calls `submit_verdict` (a forced-structure tool) to end   │
      │     the loop. Capped at MAX_TOOL_CALLS rounds.                │
      │                                                                │
      └── offline mode (no key) ──────────────────────────────────────┤
            A deterministic rule-based planner calls the same tool    │
            functions directly and applies a fixed scoring heuristic. │
                                                                       ▼
                                                          IncidentReport
                                                    (trace, verdict, confidence,
                                                     score, evidence, actions)
```

### Tools available to the agent

| Tool | Simulates | Backing data |
|---|---|---|
| `lookup_asset_criticality` | CMDB / asset inventory | `data/asset_inventory.json` |
| `lookup_ioc_reputation` | Threat-intel feed | `data/ioc_reputation.json` |
| `lookup_user_risk` | Identity provider risk signal | `data/user_risk.json` |
| `check_process_baseline` | EDR process baselining | `data/process_baselines.json` |

## Quickstart

```bash
cd soc-agent
pip install -e ".[dev]"        # add ".[dev,llm]" for the live Claude loop
pytest -q

soc-agent --alert examples/alert_c2_beacon.json
soc-agent --alert examples/alert_benign_login.json --format json
```

No install needed to just run it:

```bash
PYTHONPATH=. python3 -m soc_agent.cli --alert examples/alert_c2_beacon.json
```

### Enabling the live agent loop

```bash
pip install -e ".[llm]"
export ANTHROPIC_API_KEY=sk-ant-...
soc-agent --alert examples/alert_c2_beacon.json
```

Without a key, every report is generated by the offline planner and the
report's `mode` field reads `offline`. If a live call fails (network error,
the model exhausts its tool-call budget without submitting a verdict), the
agent transparently falls back to the offline planner and records why in
the report's `warnings`.

## Design notes / limitations

- **Backing data is synthetic**, sized for a clear demo, not production
  intel. `soc_agent/tools.py` is the seam to swap in real integrations (a
  CMDB API, MISP/OTX, an IdP risk API, an EDR platform's baseline endpoint).
- **The live loop is capped** at `MAX_TOOL_CALLS` rounds and always ends by
  calling a forced-structure `submit_verdict` tool rather than free-text —
  this keeps the final output machine-parseable regardless of what the model
  decides to investigate.
- **Offline and live modes share tool implementations**, not just their
  interface, so they can't silently drift into different answers for the
  same inputs — the scoring heuristic is the only place offline mode
  diverges from what a live model might decide.
- **Scoring is a heuristic, not a verdict of record.** It's designed to be
  transparent and auditable (every point traces to a specific piece of
  evidence in the trace) rather than maximally accurate.

## Testing

```bash
pytest -q
```

32 tests cover the tool functions, the offline planner's scoring against
three representative alerts (malicious/benign/suspicious), the live
tool-use loop via a scripted fake Anthropic client (including the
tool-call-budget and API-failure fallback paths), report rendering, and
the CLI itself as a subprocess. No network access or API key is required.
